# باشگاه ورزشی ستارگان

وب‌اپلیکیشن موبایل‌فرست (PWA) برای مدیریت باشگاه ورزشی: بازیکنان و تیم‌ها، تمرین و مسابقه، حضور و غیاب، آمار مسابقات، شهریه و مالیات، حسابداری و فروشگاه باشگاه، و داشبورد نقش‌محور مربی/مدیر. رشته باشگاه (والیبال، بسکتبال یا فوتبال) در شروع کار انتخاب می‌شود و پست‌ها، آمار و دوره‌های مسابقه بر همان اساس تنظیم می‌شوند.

## اجرا

```bash
npm install
npm run dev        # http://localhost:3000
npm run build      # ساخت نسخه تولید
npm run start      # اجرای نسخه build
```

## ورود و ثبت‌نام

صفحه ورود سه بخش دارد: ورود، ثبت‌نام بازیکن/مربی و بازیابی رمز عبور. در اولین اجرا روی دستگاهی که داده‌ای ندارد، جای این سه بخش فرم «راه‌اندازی باشگاه» نمایش داده می‌شود.

- **ثبت‌نام بازیکن** بلافاصله فعال می‌شود.
- **ثبت‌نام مربی** پس از تأیید مدیر باشگاه فعال می‌شود. درخواست‌ها در صفحه «کاربران» (`/users`) توسط مدیر بررسی می‌شوند.
- مدیر می‌تواند مستقیماً مربی تعریف کند؛ در حالت Supabase یک کد دعوت یک‌بارمصرف ۳۰ روزه ساخته می‌شود و در حالت محلی رمز عبور موقت نمایش داده می‌شود.
- تغییر رمز عبور از «تنظیمات ← امنیت حساب» انجام می‌شود. بازیابی رمز در حالت Supabase با ایمیل بازیابی و در حالت محلی با نمایش راهنما انجام می‌شود.
- **ورود سریع با تصویر پروفایل**: در حالت نمایشی، روی کارت هر حساب بزنید تا وارد شوید. اگر پروفایل تصویری ندارد، با دکمه «تصویر پروفایل» عکس چهره را انتخاب کنید (دوربین یا گالری)؛ تصویر به‌صورت مربع ۲۵۶ پیکسلی فشرده شده و به‌عنوان تصویر پروفایل همان کاربر در همان دستگاه ذخیره می‌شود و در صفحه ورود، نوار بالا، کاربران و تنظیمات نمایش داده می‌شود.
- **کارت حساب‌های واقعی رمز می‌خواهد**: وقتی باشگاه را خودتان راه‌اندازی کرده‌اید (حساب‌های واقعی)، کارت‌های صفحه ورود فقط ایمیل آن حساب را در فرم ورود پر می‌کنند و ورود بدون رمز انجام نمی‌شود؛ عنوان پنل به «حساب‌های این دستگاه» و «ورود فقط با رمز عبور شما» تغییر می‌کند. پر کردن خودکار با رمز پیش‌فرض `123456` و ورود یک‌کلیکی فقط برای حساب‌های نمونه (`manager@setaregan.ir` و…) فعال است. همچنین ساخت رمز پیش‌فرض فقط برای حساب‌های نمونه انجام می‌شود و رمز حساب‌های واقعی هرگز بازنویسی نمی‌شود.
- **ورود با اثر انگشت/چهره (WebAuthn)**: با دکمه «اثر انگشت» روی هر حساب، یک اعتبارنامه بیومتریک resident key برای آن کاربر ثبت می‌شود؛ سپس با «ورود با اثر انگشت یا چهره» بدون وارد کردن ایمیل و رمز وارد شوید. این قابلیت فقط در حالت نمایشی و روی دستگاه‌هایی با احراز هویت زیستی فعال است (در غیر این صورت پیام راهنما نمایش داده می‌شود).

### حساب‌های نمایشی (حالت محلی)

در حالت محلی، رمز عبور همه حساب‌ها `123456` است و در صفحه ورود نیز نمایش داده می‌شود:

| نقش | ایمیل | دسترسی |
| --- | --- | --- |
| مدیر باشگاه | manager@setaregan.ir | همه بخش‌ها، کاربران، حسابداری و فروشگاه |
| مربی | coach@setaregan.ir | بازیکنان، برنامه، حضور و غیاب، آمار (بدون مالی) |
| مربی در انتظار تأیید | negar@setaregan.ir | تا تأیید مدیر امکان ورود ندارد |
| بازیکن | ali@setaregan.ir | داشبورد شخصی، برنامه، آمار و شهریه خودش |

داده‌های نمونه: ۳ تیم، ۲۴ بازیکن، ۱۵ رویداد، فاکتورهای شهریه دو دوره، تراکنش‌های مالی، دو حساب (نقدی/بانکی) و سه کالای فروشگاه (والیبال).

## احراز هویت Supabase

اگر `NEXT_PUBLIC_SUPABASE_URL` و `NEXT_PUBLIC_SUPABASE_ANON_KEY` تنظیم شوند، احراز هویت واقعی Supabase فعال می‌شود؛ در غیر این صورت احراز هویت محلی (هش SHA-256 در مرورگر) استفاده می‌شود.

1. فایل `.env.local.example` را به `.env.local` کپی و کلیدهای پروژه را وارد کنید.
2. فایل `supabase/schema.sql` را در Supabase Dashboard → SQL Editor اجرا کنید. این اسکریپت شامل جدول `profiles` با وضعیت تأیید و تصویر پروفایل (`photo`)، جدول `coach_invites`، تریگر ساخت پروفایل، توابع امن `review_coach_request` و `create_coach_invite` و سیاست‌های RLS است. ستون‌های جدید `players.address`، `players.insured`، `events.reminder_note` و مقدار `training` در `player_position` با `alter ... if not exists` به پروژه‌های قبلی نیز اضافه می‌شوند (اجرای مجدد فایل امن است).
3. در تنظیمات Supabase، آدرس `http://localhost:3000/reset-password` (و دامنه تولید) را در Redirect URLs اضافه کنید.

> داده‌های باشگاه روی هر دستگاه در `localStorage` ذخیره می‌شوند و برنامه بدون اینترنت کار می‌کند. برای تبادل داده بین مدیر و مربی‌ها، `supabase/sync.sql` را هم اجرا کنید؛ جزئیات در بخش «همگام‌سازی بین دستگاه‌ها» آمده است.

## همگام‌سازی بین دستگاه‌ها (کد دعوت باشگاه)

هر دستگاه داده‌ها را در `localStorage` خودش نگه می‌دارد (آفلاین کامل کار می‌کند) و فقط رکوردهای تغییرکرده را با Supabase تبادل می‌کند. راه‌اندازی:

1. پروژه Supabase بسازید و در Vercel متغیرهای `NEXT_PUBLIC_SUPABASE_URL` و `NEXT_PUBLIC_SUPABASE_ANON_KEY` را در Environment Variables قرار دهید و دوباره Deploy کنید (این مقادیر هنگام build خوانده می‌شوند).
2. در SQL Editor ابتدا `supabase/schema.sql` و سپس `supabase/sync.sql` را اجرا کنید.
3. اولین حساب مدیر را بسازید: Authentication → Users → Add user (ایمیل و رمز، با گزینه auto-confirm). تریگر، پروفایل را می‌سازد؛ سپس در SQL Editor نقش او را مدیر کنید:

   ```sql
   update public.profiles
   set role = 'manager', status = 'active'
   where email = 'manager@example.com';
   ```

4. با همان حساب وارد برنامه شوید → تنظیمات → «همگام‌سازی مربی‌ها» → «ساخت باشگاه مشترک». کد دعوت ساخته می‌شود.
5. مربی‌ها: ثبت‌نام → تأیید ایمیل → مدیر در صفحه «کاربران» درخواست را تأیید می‌کند → مربی وارد می‌شود → تنظیمات → «پیوستن با کد دعوت».

نحوه کار:

- هر رکورد (باشگاه، تیم، بازیکن، رویداد، حضور، آمار، فاکتور، پرداخت، سرفصل، حساب، تراکنش، کالا و گردش انبار) یک سطر JSON در جدول `club_records` است؛ شناسه‌ها همان شناسه‌های متنی برنامه‌اند.
- تغییرات اول در صف محلی ذخیره و با تأخیر کوتاه ارسال می‌شوند؛ اگر اینترنت نباشد صف می‌ماند و با برگشت اینترنت ارسال می‌شود.
- دستگاه‌های دیگر تغییرات را با Realtime می‌گیرند. در اولین اتصال هر دستگاه، رکوردهای موجود روی آن آپلود و رکوردهای سرور دریافت می‌شوند.
- تعارض: آخرین ویرایش (بر اساس زمان سرور) برنده است؛ ویرایش ارسال‌نشده هر دستگاه اولویت دارد.
- حساب بازیکن به داده‌های باشگاه دسترسی ندارد؛ فقط مدیر و مربی عضو باشگاه مشترک می‌شوند.
- بدون Supabase (حالت محلی)، کارت همگام‌سازی غیرفعال است و همه‌چیز مثل قبل روی همان دستگاه می‌ماند.

> این مسیر بدون پروژه Supabase قابل آزمون نیست؛ منطق صف و ادغام با یک تست واحد محلی بررسی شده است، اما تبادل واقعی بین دو گوشی پس از تنظیم پروژه باید یک‌بار آزمایش شود.

## سرویس Go: پیمان داده رکوردها

سرویس `backend/` همان رکوردها را می‌پذیرد که برنامه در `club_records` می‌ریخت، ولی ستون‌های پرسیدنی کنار هر رکورد می‌سازد. برای اینکه هیچ فیلدی گم نشود، تست‌های قرارداد از خودِ تایپ‌های برنامه ساخته می‌شوند، نه از روی دست:

```bash
npm run codec:fixtures        # backend/testdata/payloads.json + client-fields.json
cd backend && go test ./...
```

- هر بار که به یک موجودیت فیلد جدید اضافه می‌کنید، fixtures را دوباره بسازید؛ اگر سمت سرویس آن فیلد را نشناسد، تست با نام همان فیلد شکست می‌خورد (کدک سخت‌گیرانه است و فیلد ناشناخته را رد می‌کند، نه اینکه بی‌صدا دور بریزد).
- تست‌ها بررسی می‌کنند بایت‌های payload عیناً کنار ستون‌ها ذخیره می‌شوند، هر ستون در `backend/migrations/0001_init.sql` وجود دارد، مقدار ستون‌های `ENUM` مجاز است، و `id` رکورد در پوشه با `id` داخل payload یکی است.

## حسابداری باشگاه

مدیر باشگاه از بخش «مالی» به چهار زیرصفحه دسترسی دارد:

- **شهریه**: فاکتور شهریه/مالیات، ثبت پرداخت، مطالبات و نرخ وصول. هر پرداخت به‌صورت خودکار در دفتر کل ثبت می‌شود.
- **دفتر کل**: سرفصل‌های درآمد و هزینه، ثبت تراکنش دستی (درآمد/هزینه)، فیلتر و جستجو، نمودار شش‌ماهه، تراز ماهانه و جزئیات تراکنش.
- **حساب‌ها و چک**: تعریف چند حساب بانکی و صندوق نقدی با موجودی اولیه، شماره حساب/کارت/شبا، مشاهده موجودی و چک‌های در جریان با امکان ثبت «پاس شد»، «برگشت خورد» یا بازگشت به در جریان.
- **فروشگاه و انبار**: تعریف کالا (پوشاک، تجهیزات و سایر)، ثبت خرید و فروش با روش‌های نقدی، کارت، انتقال بانکی، چک یا نسیه، محاسبه خودکار موجودی و ارزش انبار، هشدار کم‌موجودی و تاریخچه گردش انبار.
- **فروش نسیه و دریافتنی‌ها**: فروش کالا به‌صورت نسیه به‌عنوان درآمد همان روز در دفتر کل ثبت می‌شود و در صفحه «حساب‌ها و چک» به‌عنوان دریافتنی باز نمایش داده می‌شود؛ با «وصول» می‌توان مبلغ را به نقدی، کارت، انتقال بانکی یا چک تسویه کرد (وصول با چک در جریان، پس از پاس شدن چک در موجودی اعمال می‌شود و برگشت آن، فاکتور را دوباره به دریافتنی‌ها برمی‌گرداند).
- **بدهی بازیکنان (شهریه + فروشگاه)**: در فروش نسیه می‌توان «بازیکن خریدار» را انتخاب کرد تا بدهی به پرونده همان بازیکن اضافه شود. صفحه مالی کارت «بدهی بازیکنان» را نشان می‌دهد که برای هر بازیکن، مبلغ شهریه وصول‌نشده و مبلغ خرید نسیه لباس و تجهیزات را جدا و سپس جمع کل بدهی را نمایش می‌دهد؛ جمع‌های کل «مجموع شهریه»، «مجموع فروشگاه» و کل مطالبات نیز در پایین همان کارت آمده است.

قواعد مالی:

- خرید کالا یک هزینه در دفتر کل و فروش کالا یک درآمد ثبت می‌کند.
- چک «در جریان» در موجودی حساب محاسبه نمی‌شود؛ با پاس شدن، در موجودی اعمال و با برگشت، از جمع‌های معتبر حذف می‌شود.
- سرفصل‌های سیستمی (شهریه و فروش/خرید کالا) قابل حذف نیستند؛ سرفصل‌های سفارشی فقط در صورت بدون استفاده بودن حذف می‌شوند.

## رشته ورزشی و پروفایل باشگاه

- انتخاب رشته در صفحه ورود (و همچنین در پروفایل باشگاه) بین والیبال، بسکتبال و فوتبال.
- پست بازیکنان، برچسب آمار و تعداد دوره‌های مسابقه با رشته انتخاب‌شده هماهنگ می‌شوند:
  - والیبال: ست (۵ دوره) — پست‌ها: پاسور، دریافت‌کننده، مدافع میانی، پشت خط زن، لیبرو
  - بسکتبال: کوارتر (۴ دوره) — پست‌ها: گارد امتیازآور، گارد شوتزن، فوروارد کوچک، فوروارد قدرتی، سنتر
  - فوتبال: نیمه (۲ دوره) — پست‌ها: دروازه‌بان، مدافع، هافبک، مهاجم
- با تغییر رشته، پست بازیکنان فعلی به پست معادل همان رشته تبدیل می‌شود.
- در هر سه رشته، پست **«آموزشی (بدون پست)»** برای بازیکنان مدرسه/آموزشی که هنوز پست مشخصی ندارند در دسترس است (در آمار و گروه‌بندی ترکیب، بدون پست تلقی می‌شود).
- مدیر باشگاه می‌تواند در تنظیمات، نام و نام کوتاه، آرم، رشته، شهر، سال تأسیس، تلفن و فصل جاری را ویرایش کند. آرم به‌صورت Data URL (حداکثر ۶۰۰ کیلوبایت) در همان داده‌های محلی ذخیره می‌شود.

## وضعیت داده‌ها

- داده‌های باشگاه در `localStorage` همان دستگاه ذخیره می‌شوند (`valibal-club-data-v13`؛ شماره نسخه از `DEMO_DATA_VERSION` در `src/lib/seed.ts` می‌آید) و برنامه بدون اینترنت کار می‌کند. در حالت Supabase، صف تغییرات (`valibal-club-pending-v2:<clubId>`) و وضعیت آخرین همگام‌سازی (`valibal-club-seen-v2:<clubId>`) هم روی همان دستگاه نگه داشته می‌شوند.
- **برنامه با داده خالی شروع می‌شود**: در اولین اجرا روی هر دستگاه، باشگاه خالی است و صفحه ورود به جای حساب‌های نمایشی، فرم «راه‌اندازی باشگاه» را نشان می‌دهد (نام باشگاه، مدیر، ایمیل، رمز عبور و رشته). جزئیات در بخش «شروع با داده واقعی» آمده است.
- «بازیابی داده نمونه» در تنظیمات، داده نمایشی کامل را می‌سازد (برای دمو و تست)؛ «پاک کردن رکوردها» برعکس آن است: بازیکنان، تیم‌ها، رویدادها، حضور و غیاب، آمار، فاکتورها، پرداخت‌ها و انبار حذف می‌شوند ولی نام باشگاه، حساب‌های کاربری و رمزها باقی می‌مانند.
- پشتیبان‌گیری JSON از تنظیمات دو کار را ممکن می‌کند: «دانلود پشتیبان» یک فایل JSON از همه داده‌های همان دستگاه می‌سازد، و «بازگردانی پشتیبان» (فقط با حساب مدیر) همان فایل را برمی‌گرداند. فایل پشتیبان **رمز عبورها را ندارد**، پس هنگام بازگردانی یک رمز تازه برای حساب مدیر می‌گذارید و برای بقیه حساب‌ها مدیر از صفحه کاربران رمز موقت می‌سازد.

## شروع با داده واقعی

1. برنامه را باز کنید؛ چون روی دستگاه داده‌ای نیست، صفحه ورود عنوان «ساخت باشگاه شما» را نشان می‌دهد.
2. نام باشگاه، نام و نام خانوادگی مدیر، ایمیل و رمز عبور (حداقل ۶ کاراکتر) را وارد و رشته را انتخاب کنید. با «ساخت باشگاه و ورود مدیر»، حساب مدیر ساخته و وارد داشبورد می‌شوید.
3. هیچ مقدار نمونه‌ای باقی نمی‌ماند: شهر، تلفن و سال تأسیس خالی‌اند و دو حساب «صندوق باشگاه» و «حساب بانکی باشگاه» با موجودی اولیه صفر (بدون شماره کارت/شبای ساختگی) ساخته می‌شوند؛ سرفصل‌های سیستمی دفتر کل برای ثبت درآمد و هزینه آماده‌اند.
4. از همینجا بازیکن، تیم، رویداد و رکوردهای مالی واقعی را ثبت کنید. سایر مربیان از «ثبت‌نام → مربی» (نیازمند تأیید مدیر) و بازیکنان مستقیماً ثبت‌نام می‌کنند.
5. اگر قبلاً داده نمایشی روی دستگاه بوده، نسخه v13 باعث شروع مجدد با داده خالی می‌شود؛ یا از «تنظیمات → پاک کردن رکوردها» استفاده کنید.

> در حالت ابری (Supabase) این فرم نمایش داده نمی‌شود و حساب مدیر مستقیم در Supabase Auth ساخته می‌شود.

## نصب روی آیفون (PWA)

برنامه PWA است: `manifest` با `display: standalone`، `apple-touch-icon` ۱۸۰ پیکسلی، آیکون‌های ۱۹۲/۵۱۲ (و نسخه maskable) و سرویس‌ورکر فقط در حالت تولید.

1. با `npm run build` خروجی استاتیک در پوشه `out/` ساخته می‌شود (`output: "export"` در `next.config.ts`)؛ همین پوشه را روی یک آدرس **HTTPS** قرار دهید. `localhost` و IP شبکه محلی فقط برای آزمایش هستند و برای ثبت سرویس‌ورکر و WebAuthn کافی نیستند.

```bash
node scripts/serve-out.mjs 3100      # پیش‌نمایش محلی از روی out/
```
2. در Safari آیفون، آدرس را باز کنید.
3. دکمه اشتراک (Share) ← «Add to Home Screen» / «افزودن به صفحه اصلی».
4. آیکون برنامه روی صفحه Home می‌آید و با تمام‌صفحه (بدون نوار Safari) باز می‌شود.

برچسب زیر آیکون از `short_name` در `src/app/manifest.ts` و `appleWebApp.title` در `src/app/layout.tsx` می‌آید (مقدار پیش‌فرض: «باشگاه») و می‌توانید نام باشگاه خودتان را جایگزین کنید. نام باشگاه به‌صورت runtime در عنوان صفحات و نوار بالا از همان داده‌های دستگاه خوانده می‌شود.

### استقرار روی Vercel

1. مخزن را روی GitHub بفرستید و در Vercel از «Add New ← Project» اینپورتش کنید.
2. فریم‌ورک Next.js خودش تشخیص داده می‌شود؛ Build command همان `npm run build` است و چون `output: "export"` فعال است، خروجی کاملاً استاتیک سرو می‌شود (بدون Function و بدون هزینه Serverless).
3. برای حالت محلی متغیر محیطی لازم نیست. فقط اگر بعداً Supabase فعال شود، `NEXT_PUBLIC_SUPABASE_URL` و `NEXT_PUBLIC_SUPABASE_ANON_KEY` در Settings ← Environment Variables اضافه می‌شود (کلید `service_role` هیچ‌وقت اینجا نمی‌آید).
4. آدرس `*.vercel.app` که build تمام می‌شود HTTPS است و همان برای نصب روی آیفون کافی است.
5. فایل‌های مدل صدا در `public/emza` گیت‌ایگنور شده‌اند، پس Vercel آن‌ها را در زمان build دانلود می‌کند (حدود ۴۱ مگابایت). اگر میران مدل دسترسی‌پذیر نباشد، `scripts/fetch-emza-assets.mjs` دیگر build را شکست نمی‌دهد: برنامه استقرار می‌شود و فقط صدای امضا تا staged شدن فایل‌ها کار نمی‌کند (`npm run emza:assets` روی یک ماشین با اینترنت مناسب، بعد `npm run build`).
6. `next@16` به Node ۲۰.۹ به بالا نیاز دارد؛ اگر build با خطای نسخه Node مواجه شد، در Settings ← General مقدار Node.js Version را روی ۲۲ بگذارید و Redeploy کنید.

### آپدیت روی گوشی

1. تغییرات را push کنید؛ Vercel خودش build و منتشر می‌کند و آدرس عوض نمی‌شود.
2. روی گوشی اپ را کامل ببندید (App Switcher) و دوباره باز کنید. iOS همان لحظه `sw.js` را چک می‌کند، بیلد تازه را پیش‌کش می‌کند و کَش قدیمی را پاک می‌کند. اگر بار اول نسخه قدیمی ماند، یک بار دیگر ببندید و باز کنید.
3. راه قطعی، حذف آیکون از صفحه اصلی و «Add to Home Screen» دوباره است. داده در `localStorage` همان **آدرس** می‌ماند، نه در آیکون؛ با این حال قبل از هر کار دستی، «تنظیمات ← دانلود پشتیبان» را بزنید.
4. آدرس را عوض نکنید: با یک هاست یا دامنه تازه، داده‌های دستگاه روی آدرس قدیمی می‌مانند و فقط با فایل پشتیبان قابل انتقال‌اند.

### کارکرد آفلاین

`npm run build` بعد از ساخت خروجی، فهرست همه فایل‌های `out/` را داخل `out/sw.js` تزریق می‌کند (`scripts/gen-sw-manifest.mjs`) و یک شناسه نسخه به کش می‌دهد. سرویس‌ورکر در اولین بازدید آنلاین همه آن فایل‌ها را ذخیره می‌کند، بنابراین بعد از یک بار باز کردن، برنامه بدون هیچ اینترنتی باز می‌شود و جابه‌جایی بین صفحه‌ها هم کار می‌کند (درخواست‌های `?_rsc` از کش پاسخ می‌گیرند). با هر build جدید نسخه کش عوض می‌شود و نسخه قدیمی پاک می‌شود.

> قبل از تست آفلاین، یک بار نسخه جدید را آنلاین باز کنید تا سرویس‌ورکر تازه نصب و کش پر شود. داده‌ها در `localStorage` همان دستگاه هستند و به شبکه کاری ندارند.

> فایل نصبی مستقل (`.ipa`) برای آیفون وجود ندارد مگر از راه App Store یا ابزارهای توسعه‌دهنده. برای انتشار روی App Store می‌توان همین برنامه را با Capacitor در یک پروژه iOS قرار داد که به macOS، Xcode و اکانت Apple Developer نیاز دارد. مسیر پیشنهادی و کم‌هزینه همین PWA روی HTTPS است.

## نکات فنی

- Next.js 16 (App Router) + React 19 + TypeScript strict + Tailwind CSS v4
- رابط فارسی RTL با فونت Vazirmatn و تاریخ شمسی (`Intl.DateTimeFormat` با `fa-IR` / تقویم persian)
- **همه تاریخ‌ها شمسی است**: فیلدهای ورودی تاریخ (`JalaliDateInput` در `src/components/ui.tsx`) با فرمت `۱۴۰۵/۰۸/۰۳` و دکمه «امروز» کار می‌کنند، ارقام فارسی و عربی را می‌پذیرند و تاریخ نامعتبر را با حلقه قرمز نشان می‌دهند. تبدیل با `jalaali-js` انجام می‌شود ولی ذخیره در داده‌ها همان فرمت گرگوری `YYYY-MM-DD` است، پس نیازی به مهاجرت داده نبود.
- PWA: `src/app/manifest.ts` و `public/sw.js`؛ سرویس‌ورکر فقط در تولید ثبت می‌شود
- **خروجی استاتیک**: `output: "export"` + `trailingSlash: true` تا برنامه بدون سرور روی هر هاست HTTPS اجرا شود. چون فایل `index.html` برای هر مسیر ساخته می‌شود، صفحه‌های جزئیات به جای مسیر پویا (`/players/[id]`) با پارامتر کوئری باز می‌شوند: `/players/?id=p-123`، `/schedule/?id=…`، `/teams/?id=…`. در هر بخش `page.tsx` (سرور + `Suspense`)، `view.tsx` (درِ `useSearchParams`)، `list.tsx` و `detail.tsx` جدا هستند.
- اگر هاست شما index دایرکتوری را پشتیبانی نکند، نشانی‌های `/players/` با بارگذاری مستقیم ۴۰۴ می‌دهند (ناوبری درونی برنامه سمت کلاینت است و مشکل ندارد)؛ در آن حالت `trailingSlash: false` و مسیرهای `.html` را امتحان کنید.
- ساختار:
  - `src/app/(app)/` صفحات اصلی: داشبورد، بازیکنان، تیم‌ها، برنامه، مالی (شهریه، دفتر کل، حساب‌ها، فروشگاه)، کاربران، تنظیمات
  - `src/lib/` انواع، داده نمونه، استور Context، احراز هویت محلی/ابری، توابع مالی، تاریخ و برچسب‌ها
  - `src/components/` کامپوننت‌های مشترک و شیت‌های فرم
  - `supabase/schema.sql` اسکیمای احراز هویت، تأیید مربی و RLS
  - `supabase/sync.sql` همگام‌سازی رکوردها: باشگاه مشترک، کد دعوت، جدول `club_records`، RLS و Realtime
  - `src/lib/record-sync.ts` و `src/lib/use-record-sync.ts` صف تغییرات، ادغام رکوردها و اتصال زنده
  - `src/lib/emza.ts` و `src/lib/emza-training.ts` موتور فرمان فارسی دستیار «امضا» و تولید برنامه تمرینی
  - `src/lib/emza-asr.ts` ضبط میکروفون، تشخیص سکوت و ارسال صدا به کارگر محلی؛ `public/emza/asr-worker.js` اجرای Whisper روی دستگاه
  - `src/components/emza-agent.tsx` دکمه شناور، پنل گفتگو و صدا؛ `src/components/emza-settings.tsx` کلید فعال‌سازی
  - `scripts/fetch-emza-assets.mjs` و `scripts/gen-sw-manifest.mjs` آماده‌سازی مدل گفتار و فهرست پیش‌کش سرویس‌ورکر

## دستیار صوتی «امضا»

امضا به‌طور پیش‌فرض روشن است و دکمه دایره‌ای پایین صفحه (سمت چپ) وضعیتش را نشان می‌دهد؛ از تنظیمات هم می‌توان خاموشش کرد. در حالت عادی فقط گوش می‌دهد و چیزی نشان نمی‌دهد: به‌محض شنیدن نامش («امضا، …») نامش کنار دایره ظاهر می‌شود و رنگ دایره عوض می‌شود — قرمز هنگام گوش‌دادن، کهربایی وقتی صدا زده شود و سبز هنگام پاسخ‌دادن.

- **تشخیص گفتار روی خود دستگاه**: مدل `whisper-tiny` (نسخه فشرده چندزبانه) با `transformers.js` داخل یک Web Worker و با WebAssembly اجرا می‌شود. هیچ صدایی به گوگل، سرور یا API نمی‌رود و پس از نخستین دانلود، بدون اینترنت هم کار می‌کند.
- **دانلود یک‌بارهٔ ۷۰ مگابایت**: فایل‌های مدل و موتور اجرا (`onnxruntime-web`، نسخهٔ asyncify که روی iOS به `SharedArrayBuffer` نیاز ندارد) در `public/emza/` قرار می‌گیرند و به همین دلیل سرویس‌ورکر آن‌ها را برای همیشه در حافظهٔ دستگاه نگه می‌دارد. مرحلهٔ دانلود با عدد مگابایت درون پنل و کنار دکمه دیده می‌شود.
- **آماده‌سازی فایل‌ها در زمان ساخت**: `npm run build` ابتدا `scripts/fetch-emza-assets.mjs` را اجرا می‌کند؛ این اسکریپت فایل‌های مدل را از Hugging Face (و در صورت قطعی، از آینهٔ `hf-mirror.com`) با قابلیت ادامهٔ دانلود می‌گیرد و فایل‌های موتور را از `node_modules` کپی می‌کند. فایل‌های سنگین در گیت ignore شده‌اند.
- **قطعه‌بندی خودکار صدا**: میکروفون با `getUserMedia` گرفته می‌شود، سطح انرژی صدا سنجیده می‌شود و هر جمله پس از ۰٫۷ ثانیه سکوت جدا و به ۱۶ کیلوهرتز تبدیل می‌شود؛ بنابراین امضا بی‌وقفه گوش می‌دهد ولی فقط وقتی حرفی گفته شود پردازش می‌کند.
- **محدودیت‌های پلتفرم**: آی‌اواس پیش از نخستین لمس اجازهٔ میکروفون نمی‌دهد؛ امضا پس از اولین لمس (یا لمس دکمه) گوش‌دادن را شروع می‌کند. اگر میکروفون اجازه نداشته باشد یا WebAssembly پشتیبانی نشود، لمس دکمه پنل گفتگو را باز می‌کند تا فرمان را تایپ کنید.
- **پاسخ صوتی**: پاسخ با `speechSynthesis` خوانده می‌شود؛ اگر متن پاسخ فارسی باشد صدای `fa-*` و اگر انگلیسی باشد صدای `en-*` انتخاب می‌شود. اگر هیچ‌کدام روی دستگاه نصب نباشد فقط متن نمایش داده می‌شود (بدون ارسال متن به سرویس ابری).
- **اجرای فرمان‌ها آفلاین است**: فرمان روی همان داده‌های `localStorage` اجرا می‌شود و نیازی به سرور یا مدل زبانی ندارد.
- **فرمان‌های پشتیبانی‌شده** (نمونه):
  - «یک بازیکن به نام علی رضایی با موبایل ۰۹۱۲۳۴۵۶۷۸۹ و پیراهن شماره ۱۰ برای تیم جوانان ثبت کن» (پست، قد، شهریه، بیمه و آدرس هم قابل ذکر است)
  - «تیم امید با مربی رضا محمدی بساز»
  - «تمرین تیم جوانان فردا ساعت ۱۸ ثبت کن» / «مسابقه با سپاهان جمعه ساعت ۲۰»
  - «علی رضایی را در تمرین غایب کن»
  - «برای علی رضایی فاکتور شهریه ۵۰۰ هزار تومان صادر کن» و «علی رضایی ۲۰۰ هزار تومان پرداخت کرد»
  - «هزینه ۲۰۰ هزار تومان بابت توپ ثبت کن»
  - «یک پیشنهاد تمرین والیبال بده» و «همین برنامه را فردا ساعت ۱۹ ثبت کن»
  - «بدهی علی چقدر است؟»، «چند بازیکن داریم؟»، «تمرین بعدی کی است؟»، «بدهکاران را نشان بده»
  - «برو به فروشگاه»، «صفحه مالی را باز کن»
- **پیشنهاد تمرین والیبال** از داده‌های خود باشگاه ساخته می‌شود: فاصله از آخرین تمرین، مسابقه پیش‌رو، نسبت خطا/حمله/بلوک/سرویس/رویش در آمار، تعداد پاسور و لیبرو و نرخ حضور بازیکنان. اگر «ثبت کن» بگویید، برنامه با جزئیات در یادداشت رویداد و یادآوری ذخیره می‌شود.
- **دسترسی نقش‌محور**: ثبت مالی (فاکتور، پرداخت، دفتر کل) فقط با حساب مدیر ممکن است و برای مربی پیام محدودیت می‌دهد.
- **فرمان انگلیسی**: همان کارها به انگلیسی هم گفته یا نوشته می‌شود؛ مثال‌های زیر در حالت فارسی یا انگلیسی برنامه کار می‌کنند.

## دوزبانه: فارسی و انگلیسی

- **سوییچ زبان**: آیکون زبان در هدر و پایین صفحهٔ ورود؛ انتخاب در `localStorage` با کلید `valibal-locale-v1` می‌ماند و همان لحظه به کل برنامه اعمال می‌شود (بدون بارگذاری دوباره).
- **زیرساخت** در `src/lib/i18n/`: `locale.ts` استور لوکل + `dir`/`lang` سند + `{name}` interpolation، `bilingual.ts` با `bi(fa, en)` و `bilingual()` برای جدول برچسب‌ها، و `messages.ts` که همهٔ متن‌های رابط را گروه‌به‌گروه نگه می‌دارد. کامپوننت‌ها با `useT()` و ماژول‌های ساده با `tr()` متن را می‌خوانند.
- **تقویم شمسی در هر دو زبان**: در حالت انگلیسی هم تاریخ‌ها شمسی‌اند با ارقام لاتین («23 Aban 1405»); فقط نام ماه/روز و جداکننده‌ها انگلیسی می‌شوند. عددها، درصد و «تومان» هم با `Intl` همان لوکل قالب‌بندی می‌شوند.
- **جهت صفحه**: `rtl`/`ltr` روی سند و کلاس‌های منطقی (`ms-*`, `me-*`, `text-start/end`, `start-*`, `rounded-ss/se`) در همه‌جا به‌کار رفته تا چیدمان آینه‌ای بماند.
- **داده‌ها ترجمه نمی‌شوند**: نام بازیکن، تیم، سالن و یادداشت‌ها همان چیزی می‌ماند که ثبت شده است. دو استثنا: (۱) متادیتای زمان ساخت (`src/app/layout.tsx` و `src/app/manifest.ts`) دوزبانه نوشته شده، چون خروجی استاتیک فقط یک نسخهٔ متادیتا دارد؛ (۲) نام‌هایی که برنامه در نخستین اجرا خودش می‌سازد (باشگاه بی‌نام، سرفصل‌های دفتر کل و حساب‌های اولیه) به زبانی نوشته می‌شوند که برنامه در آن لحظه باز است و بعد از آن مثل هر دادهٔ دیگری قابل ویرایش‌اند.
- **گفتار دوزبانه امضا**: زبان تشخیص گفتار (`whisper`) و واژه‌های راهنمای آن در `public/emza/asr-worker.js` از لوکل فعلی گرفته می‌شود؛ در حالت انگلیسی روی `en` و در حالت فارسی روی `fa` تنظیم می‌شود و فیلتر «همه‌واژه‌های تو‌خالی» فقط روی متن فارسی اعمال می‌شود.
- **صفحهٔ آفلاین**: پیام «این صفحه ذخیره نشده» در `public/sw.js` هر دو زبان را دارد، چون سرویس‌ورکر از لوکل برنامه خبر ندارد.
- **خطاهای سرور**: مسیر `/api/auth/bootstrap-manager` به‌جای متن فارسی، `code` برمی‌گرداند و برنامه پیام دوزبانهٔ متناظر را نشان می‌دهد.
- **امضای دوزبانه**: نام بیدارکننده «امضا» و `emza` هر دو هستند و فرمان‌ها با واژگان فارسی یا انگلیسی شناخته می‌شوند؛ پاسخ هم به همان زبانی است که کاربر در آن کار می‌کند (متن پاسخ از `messages.ts` می‌آید).
